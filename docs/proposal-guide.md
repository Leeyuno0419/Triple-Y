# Claude 기획서 작성 지침서

Triple Y 팀원이 Claude(Claude Code 등)로 기획서를 작성·수정할 때 따르는 규칙.
팀원 누가 Claude를 쓰더라도 같은 형식과 기준으로 문서가 유지되도록 하는 것이 목적이다.
프로젝트 공통 규칙은 [CLAUDE.md](../CLAUDE.md)를 따르고, 이 문서는 기획서 작업에만 적용한다.

---

## 1. 대상 파일

| 파일 | 역할 |
|---|---|
| `docs/proposal.md` | 기획서 원본. **수정은 항상 이 파일에서** 한다. |
| `docs/proposal.pdf` | 제출·공유용. md를 고친 뒤 다시 만든다 (직접 편집 금지). |
| `docs/proposal-guide.md` | 이 지침서. 규칙을 바꿀 때는 팀 합의 후 수정한다. |

## 2. 문서 구조

- 목차(1~13장 + 변경 이력)와 장 번호를 유지한다.
- 장을 추가·삭제·재배치하는 것은 팀 합의 후에만 한다.
- 4장 **핵심 기능** = 확정된 기본틀. 9장 **추가 기능 후보** = 토론 대상. 둘을 섞지 않는다.

## 3. 표기 규칙

| 표기 | 의미 | 예 |
|---|---|---|
| 일반 서술 | 팀이 확정한 내용 | F1 인원 계수·밀집도 추정 |
| `[토론]` | 아직 합의 전, 회의에서 정할 내용 | 정량 목표 수치 `[토론]` |
| `(확인 필요)` | 출처·수치·이용 조건을 아직 검증하지 못함 | 데이터셋 라이선스 (확인 필요) |
| (미정) | 정보 자체가 아직 없음 | 수행 기간 (미정) |

- 합의가 끝나면 `[토론]`을 지우고, 검증이 끝나면 `(확인 필요)`를 지우고 출처를 13장에 추가한다.

## 4. 내용 작성 원칙

- **사실을 지어내지 않는다.** 통계, 사고 수치, 논문, 데이터셋 크기·라이선스, API 이름은 확인된 것만 쓴다. 확인하지 못했으면 `(확인 필요)`를 붙인다.
- 새 논문·자료를 인용하면 13장 참고 자료에 저자·연도·제목을 추가한다.
- 팀이 정하지 않은 결정(모델 선택, 역할, 일정, 목표 수치)을 Claude가 확정하지 않는다. 제안은 `[토론]`을 붙여 쓴다.
- 사고 관련 서술은 사실 위주로, 피해자를 자극적으로 묘사하지 않는다.

## 5. 문체

- 한국어, 개조식(`-` 목록)과 표 위주. 문장은 짧게, 한 문장에 한 가지 내용.
- 문장 끝은 "~한다 / ~이다" 체로 통일한다.
- 전문용어는 처음 나올 때 한 줄로 풀이한다 (예: 4장 "용어 풀이").
- 코드·파일명·식별자는 `백틱`으로 감싼다.
- 다이어그램은 코드블록 텍스트로 그린다 (GitHub와 PDF 모두에서 깨지지 않도록). Mermaid는 PDF에서 그림으로 나오지 않으므로 쓰지 않는다.
- 한글이 들어간 줄 오른쪽에 `│` 같은 테두리를 두지 않는다. 한글 폭이 글꼴마다 달라 상자가 어긋난다. 5장처럼 왼쪽 정렬 화살표(`├──▶`, `▼`)만 쓴다.
- 목록(`-`, `1.`)이나 표 바로 앞에는 빈 줄을 둔다. 빈 줄이 없으면 PDF 변환 시 목록이 문단으로 붙어 버린다.

## 6. 추가 기능(9장) 다루는 법

- 9장은 표 두 개로 나뉜다. 9.1 후보 목록(후보 기능 / 설명 / 기대 효과 / 난이도), 9.2 의견 및 결정(팀원 3명 의견 / 결정).
- 새 후보는 9.1과 9.2에 같은 ID로 한 행씩 추가한다. ID는 A10, A11… 순서로 이어 붙인다.
- 팀원 의견 칸은 **해당 팀원이 말한 내용만** 적는다. Claude가 대신 채우지 않는다.
- 결정이 `채택`이면:
  1. 4장 표에 F6, F7… 로 옮기고 5장 구조·11장 일정에 반영한다.
  2. 9.2 결정 칸에는 `채택 → F6`처럼 남긴다 (행을 지우지 않는다).
- `보류`·`기각`은 사유를 한 줄 적는다.

## 7. 수정 후 할 일 (체크리스트)

1. 문서 끝 **변경 이력**에 한 줄 추가 (버전, 날짜, 작성자, 내용). 작은 수정은 v0.1 → v0.2, 팀 확정본은 v1.0.
2. 문서 상단 "문서 상태"의 버전·날짜를 갱신한다.
3. `docs/proposal.pdf`를 다시 만든다 (8장).
4. CLAUDE.md의 Git 규칙대로 브랜치(`feat/proposal-내용`, 예: `feat/proposal-data-section`)에서 작업하고 PR을 올린다. 커밋 메시지는 `docs: 내용`.
5. 기획서는 한 번에 한 명만 수정하도록 팀 채팅에 미리 알린다 (충돌 방지).

## 8. PDF 다시 만들기

Claude에게 "기획서 PDF 다시 만들어줘"라고 요청하면 아래 방식으로 만든다.

1. `docs/proposal.md`를 Python `markdown` 패키지(`tables`, `fenced_code` 확장)로 HTML로 바꾼다.
2. HTML에 인쇄용 CSS를 넣는다: 글꼴 맑은 고딕(`Malgun Gothic`), A4, 여백 약 18mm, 표 테두리, 코드블록은 고정폭 글꼴(`D2Coding` 또는 `Consolas`)과 줄바꿈 없음.
3. Chrome 헤드리스로 인쇄한다.
   ```powershell
   & "C:\Program Files\Google\Chrome\Application\chrome.exe" --headless --disable-gpu --no-pdf-header-footer --print-to-pdf="docs\proposal.pdf" "임시HTML경로"
   ```
4. 변환용 임시 HTML·스크립트는 저장소에 넣지 않는다.
5. 만든 PDF를 열어 한글 깨짐, 표 잘림, 다이어그램 정렬을 확인한다.

- `markdown` 패키지는 Anaconda에 기본 포함되어 있다. 없는 환경이라면 설치 전에 팀에 먼저 알린다 (CLAUDE.md 패키지 규칙).

## 9. 팀원용 예시 요청

```
docs/proposal-guide.md 규칙에 따라 기획서 6장 데이터를 조사해서 채워줘.
확인 못 한 건 (확인 필요)로 남겨줘.
```
```
기획서 9장에 추가 기능 후보로 "드론 영상 분석"을 넣어줘. 내 의견 칸(조영준)에는 "찬성 - 넓은 지역 커버" 라고 적어줘.
```
```
회의 결과 A2, A7 채택. 4장으로 옮기고 일정에 반영한 다음 PDF도 다시 만들어줘.
```
```
기획서에서 [토론]과 (확인 필요) 남은 곳 목록만 뽑아줘. 수정은 하지 마.
```
