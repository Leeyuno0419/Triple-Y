# Claude 기획서 작성 지침서

Triple Y 팀원이 Claude(Claude Code 등)로 기획서를 작성·수정할 때 따르는 규칙.
팀원 누가 Claude를 쓰더라도 같은 형식과 기준으로 문서가 유지되도록 하는 것이 목적이다.
프로젝트 공통 규칙은 [CLAUDE.md](../CLAUDE.md)를 따르고, 이 문서는 기획서 작업에만 적용한다.

---

## 1. 대상 파일

| 파일 | 역할 |
|---|---|
| `docs/proposal.md` | **제출용 요약본**. 범위(MVP)·담당·일정의 기준. 수정은 항상 md에서 한다. |
| `docs/proposal.pdf` | 제출·공유용. md를 고친 뒤 다시 만든다 (직접 편집 금지). |
| `docs/proposal-detail.md` | **내부용 상세 문서**. 설계 근거·수식, 기술 비교, 사업성, 실험 계획, 여유 시 기능 설계, 예상 질문. |
| `docs/references.md` | 두 문서가 함께 쓰는 출처 목록. |
| `Images/proposal/*.svg` | 요약본 그림. `Images/proposal/full/`은 상세 문서 그림(축소 전 전체 범위). |
| `docs/proposal-guide.md` | 이 지침서. 규칙을 바꿀 때는 팀 합의(PR 리뷰) 후 수정한다. |

- 요약본과 상세 문서의 내용이 다르면 **요약본이 기준**이다. 상세 문서에는 요약본을 가리키는 안내를 둔다.

## 2. 문서 구조

- 요약본은 강사 제출 양식 7항목을 따른다: 1 개요 / 2 문제점 / 3 해결 방안 / 4 유저 시나리오 / 5 시스템 설계도 / 6 깃허브 / 7 그 외 + 변경 이력.
- 요약본 본문은 10쪽 내외로 유지한다. 길어지는 비교표·분석·예상 질문은 상세 문서로 옮기고 요약본에는 한 줄 요약과 링크만 둔다.
- 장 번호와 순서를 바꾸는 것은 팀 합의 후에만 한다.

## 3. 표기 규칙

| 표기 | 의미 | 예 |
|---|---|---|
| 일반 서술 | 팀이 확정한 내용 | 인원 추정은 P2PNet을 쓴다 |
| `(가정)` | 근거 자료가 없어 팀이 정한 설계값. 실험으로 검증한다 | 등급 하강 10초 유지 (가정) |
| `[토론]` | 아직 합의 전, 회의에서 정할 내용 | 시연 구역 `[토론]` |
| `(확인 필요)` | 출처·수치·이용 조건을 아직 검증하지 못함 | 조달 단가 (확인 필요) |
| (미정) | 정보 자체가 아직 없음 | 예산 (미정) |
| `[n]` | `references.md`의 출처 번호 | 군중 압력 0.02/s² [1] |

- 합의가 끝나면 `[토론]`을 지우고, 검증이 끝나면 `(확인 필요)`를 지우고 출처를 추가한다.
- PDF에서는 `(가정)`과 `(확인 필요)`가 작은 배지로 표시된다.

## 4. 내용 작성 원칙

- **사실을 지어내지 않는다.** 통계, 사고 수치, 논문, 모델 성능, 데이터셋 조건, API 정보는 원문을 확인한 것만 쓴다. 확인하지 못했으면 빼거나 `(확인 필요)`를 붙인다.
- 새 출처는 `references.md` 끝에 다음 번호로 추가한다. **기존 번호는 바꾸거나 지우지 않는다** (두 문서의 인용이 깨진다).
- 팀이 정하지 않은 결정(모델 선택, 역할, 일정, 목표 수치)을 Claude가 확정하지 않는다. 제안은 `[토론]`이나 `(가정)`을 붙여 쓴다.
- 사고 관련 서술은 사실 위주로, 피해자를 자극적으로 묘사하지 않는다.

## 5. 문체

- 한국어, 개조식(`-` 목록)과 표 위주. 문장은 짧게, 한 문장에 한 가지 내용.
- 문장 끝은 "~한다 / ~이다" 체로 통일한다.
- 전문용어는 처음 나올 때 한 줄로 풀이한다.
- 코드·파일명·식별자는 `백틱`으로 감싼다.
- 그림은 diagram-design 스킬로 만든 SVG를 `Images/proposal/`에 두고 md에서 이미지로 참조한다 (GitHub와 PDF 모두 표시된다). 간단한 구조는 코드블록 텍스트로 그려도 된다. Mermaid는 PDF에서 그림으로 나오지 않으므로 쓰지 않는다.
- 코드블록 텍스트 그림에서 한글이 들어간 줄 오른쪽에 `│` 같은 테두리를 두지 않는다. 한글 폭이 글꼴마다 달라 어긋난다.
- 수식에 결합 문자(ρ̂, v̄ 등)를 쓰지 않는다. PDF에서 글자가 어긋난다. `ρ*`, `V_c`처럼 쓴다.
- 목록(`-`, `1.`)이나 표 바로 앞에는 빈 줄을 둔다. 하위 목록은 4칸 들여쓴다.

## 6. 여유 시 기능 다루는 법

- MVP 밖 기능은 요약본 1.3 "여유 시" 칸에 우선순위 순서로 적고, 설계는 상세 문서에 둔다.
- 여유 시 기능을 MVP로 올리려면 팀 합의 후 요약본의 기능·담당(3.4), 진행 단계(3.5), 일정(7.4)을 함께 고친다.
- 기능을 만들기 전에는 상세 문서의 해당 절(3.4 AI 핵심 로직, 5장 설계 등)을 먼저 읽는다.

## 7. 수정 후 할 일 (체크리스트)

1. 문서 끝 **변경 이력**에 한 줄 추가 (버전, 날짜, 작성자, 내용). 작은 수정은 v2.0 → v2.1, 큰 개편은 v3.0.
2. 문서 상단 "문서 상태"의 버전·날짜를 갱신한다.
3. `docs/proposal.pdf`를 다시 만든다 (8장).
4. CLAUDE.md의 Git 규칙대로 브랜치(`feat/proposal-내용`)에서 작업하고 PR을 올린다. 커밋 메시지는 `docs: 내용`.
5. 기획서는 한 번에 한 명만 수정하도록 팀 채팅에 미리 알린다 (충돌 방지).

## 8. PDF 다시 만들기

Claude에게 "기획서 PDF 다시 만들어줘"라고 요청하면 아래 방식으로 만든다.

1. `docs/proposal.md`를 Python `markdown` 패키지(`tables`, `fenced_code`, `sane_lists` 확장)로 HTML로 바꾼다.
2. `references.md`에서 **본문에 인용한 번호만** 골라 "부록. 참고 문헌"으로 변경 이력 앞에 붙인다.
3. 인쇄용 CSS를 넣는다: 글꼴 맑은 고딕(`Malgun Gothic`), A4, 여백 약 17~18mm, 표 테두리, 장(`##`)마다 새 쪽, 코드블록은 `Consolas`, 기능 ID·날짜는 줄바꿈 금지, `(가정)`·`(확인 필요)`는 배지.
4. Chrome 헤드리스로 인쇄한다. **실행 중인 Chrome과 분리하도록 별도 프로필 폴더를 꼭 지정한다** (지정하지 않으면 열려 있는 Chrome이 명령을 가로채 PDF가 만들어지지 않는다).
   ```powershell
   & "C:\Program Files\Google\Chrome\Application\chrome.exe" --headless=new --disable-gpu --no-pdf-header-footer --user-data-dir="$env:TEMP\proposal-chrome" --print-to-pdf="임시폴더\out.pdf" "임시HTML경로"
   ```
5. 임시 폴더에 만든 PDF를 `docs/proposal.pdf`로 복사한다. **`docs/proposal.pdf`가 PDF 뷰어나 브라우저에 열려 있으면 덮어쓸 수 없으니 먼저 닫는다.**
6. 변환용 임시 HTML·스크립트는 저장소에 넣지 않는다.
7. 만든 PDF를 열어 한글 깨짐, 표 잘림, 그림 정렬을 확인한다.

- `markdown` 패키지는 Anaconda에 기본 포함되어 있다. 없는 환경이라면 설치 전에 팀에 먼저 알린다 (CLAUDE.md 패키지 규칙).

```

```
