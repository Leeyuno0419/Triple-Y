> CCTV 영상 한 편이 상황실 화면의 히트맵과 알림이 되기까지의 과정을 단계별로 풀어 쓴 문서다.
> 대상은 AI 기초 수업을 듣는 학생이다. 모르는 용어는 [glossary.md](glossary.md)에서 찾는다.
> 2026-11-11 기준 코드 상태를 적었다. 기준 문서는 [proposal.md](proposal.md), [timeline-spec.md](timeline-spec.md), [api-spec.md](api-spec.md)다.

## 0. 한 장 요약

```
 ┌──────────────── 1부. 사전 분석 (Python, 시연 전에 한 번) ────────────────┐

  ① 영상 준비          AI Hub 영상 → data/processed/g1/E04_039.mp4
        ↓
  ② 구역 설정          바닥 지도 공식(호모그래피), 걸을 수 있는 영역, 설정값
        ↓               → infra/homography/E04_039.json
  ③ 셀 만들기          바닥을 2m × 2m 칸으로 나눈다
        ↓
  ④ 인원·밀도  (이유노)   머리 찾기 → 바닥 위치 → 칸마다 사람 수 ÷ 면적
        ↓               → timeline.json에 density, count 채움
  ⑤ 흐름·불안정 (조영준)  움직임 재기 → 속도, 흔들림, 군중 압력, 유입 비율
        ↓               → vx, vy, speed_var, pressure, inflow_ratio 채움
  ⑥ 60초 예측  (나예린)   최근 30초 밀도 → 60초 뒤 밀도
        ↓               → density_pred_60s 채움
  📄 timeline.json  (1초마다 칸별 숫자만 담긴 기록표)

 └─────────────────────────────────────────────────────────────────────────┘
        ↓
 ┌──────────────── 2부. 시연 (실시간처럼 재생) ─────────────────────────────┐

  ⑦ 서버 (조영준, Spring Boot)   1초에 한 줄씩 꺼냄 → 등급 판정 → 알림 결정
        ↓  WebSocket
  ⑧ 화면 (나예린, React)         영상 위 히트맵, 그래프, 알림 목록

 └─────────────────────────────────────────────────────────────────────────┘
```

**핵심 아이디어 두 가지**

1. **분석과 시연을 나눈다.** 지금 컴퓨터(CPU)로는 3분 영상 분석에 약 8분 반이 걸려 실시간이 안 된다. 그래서 미리 분석해 결과를 파일로 저장하고, 시연 때는 그 파일을 1초씩 재생한다. 녹화 방송처럼 미리 만들어 두고 정해진 시간에 내보내는 방식이다.
2. **세 사람이 파일 하나로만 주고받는다.** 모든 결과는 `timeline.json`이라는 한 파일에 같은 규칙(규격)으로 쌓인다. 그래서 각자 따로 만들 수 있고, 진짜 데이터가 나오기 전에는 가짜 파일로 개발한다.

### ② 구역 설정: 비스듬한 화면을 바닥 지도로 펴기

**왜 필요한가**: CCTV는 비스듬히 내려다보며 찍는다. 그래서 화면 아래쪽(가까운 곳)의 1m는 길게, 위쪽(먼 곳)의 1m는 짧게 보인다. 화면 픽셀로는 넓이를 잴 수 없으니, 화면을 위에서 내려다본 지도(바닥 좌표, 단위 m)로 펴야 "1㎡당 몇 명"을 계산할 수 있다.

**호모그래피**는 이 "펴는 공식"이다. 3×3 숫자표 하나이고, 화면 위 점(픽셀)을 넣으면 바닥 위 점(m)이 나온다.

```
  화면 (비스듬히)                      바닥 지도 (위에서 본 모습)
   ╱‾‾‾‾‾‾‾‾╲      호모그래피 H         ┌──────────┐
  ╱  · ·  ·  ╲    ─────────────▶       │ ·  ·   · │
 ╱  ·   ·  ·  ╲                        │  ·   ·  ·│
╱______________╲                       └──────────┘
 (먼 곳은 작게)                          (어디서나 같은 축척)
```

**공식을 만드는 법**: 바닥에서 실제 크기를 아는 것을 찾아 화면 위치와 짝짓는다. 영상마다 쓸 수 있는 것이 달라서 세 가지 방법을 썼다.

| 영상 | 기준으로 쓴 것 | 방법 |
|---|---|---|
| `E04_022` | 바닥의 체크무늬 타일 (한 칸 15cm) | 타일 모서리를 자동으로 찾아 맞춤 (RANSAC으로 엉터리 점 제거) |
| `E04_039` | 빨간 미끄럼방지 띠, "30" 속도제한 노면 표시 | 띠 경계선과 노면 표시 크기(2.0m × 2.8m 규격)로 맞춤 |
| `E05_035` | 바닥 기준이 없음 → **서 있는 사람 11명** | 발에서 머리까지 높이(평균 1.55m 가정)로 카메라 높이·각도를 거꾸로 계산 (`camera_fit.py`) |

**머리 높이 평면**: AI가 찾는 것은 발이 아니라 **머리** 위치다. 머리는 바닥보다 약 1.5m 높은데, 바닥용 공식에 머리 점을 넣으면 실제보다 카메라에서 먼 곳으로 밀린다(`E04_039`에서 2.4m). 그래서 "바닥에서 1.5m 떠 있는 가상의 판" 기준 공식을 따로 만들어 머리 점에 쓴다. 이렇게 하니 오차가 0.2m로 줄었다.

```
  카메라 ●
          ╲  ← 머리를 지나는 시선
           ╲
            ● 머리 (높이 1.5m)        ← 머리 높이 평면 공식은 여기서 바로 아래 바닥(✓)을 준다
            │╲
            │ ╲
   ─────────✓──✗────────── 바닥     ← 바닥 공식에 머리 점을 넣으면 시선이 바닥에 닿는 곳(✗)이 나온다
           실제  잘못된 위치(밀림)
```

**구역 설정 파일**(`infra/homography/영상이름.json`)에 함께 저장하는 것:

| 키 | 내용 |
|---|---|
| `H_img_to_ground` | 바닥용 공식 |
| `head_plane` | 머리 높이 평면용 공식 |
| `walkable_polygon_px` | 사람이 걸을 수 있는 영역 (화면 위 다각형). 벽·가게 안은 뺀다 |
| `cell_origin_m` | 칸을 어디서부터 나눌지 |
| `counter` | 머리 찾기 설정값 (축소 배율, 판정 기준, 평균 장수). ④에서 쓴다 |
| `scale_assumption`, `scale_checks` | 축척의 근거와 검증값 (트럭 폭, 골목 폭 등이 상식과 맞는지) |

### ③ 셀 만들기

바닥 지도를 **2m × 2m 칸(셀)**으로 나눈다. 칸마다 다음을 계산해 `timeline.json`의 `meta.cells`에 적는다.

- `cell_id`: 칸 이름. `c-0403`은 4행 3열이다.
- `walkable_area_m2`: 칸 안에서 실제로 걸을 수 있는 넓이. 칸 안에 점 400개를 찍어 걸을 수 있는 영역 안에 든 비율로 구한다. 벽에 걸친 칸은 4㎡보다 작다.
- `image_polygon`: 칸의 네 모서리를 화면 위치로 되돌린 것. 화면에 히트맵을 그릴 때 쓴다.

걸을 수 있는 넓이가 1㎡ 미만인 자투리 칸은 뺀다. 한 명만 잘못 세도 밀도가 크게 튀기 때문이다.

### ④ 인원·밀도 (이유노, `src/counting/run_density.py`)

1초마다 다음을 한다.

```
 ┌ 1초 = 30프레임 ─────────────────────────────┐
 │ t−0.4초  t−0.2초   t초   t+0.2초  t+0.4초   │  ← 5장을 뽑는다
 └─────────────────────────────────────────────┘
        │ 각 장마다
        ▼
  (a) 영상 축소           0.25배 등으로 줄인다 (영상마다 E2로 고른 값)
  (b) P2PNet             머리마다 점 + "머리일 확률" 점수
  (c) 판정 기준           점수가 기준(예: 0.2)보다 높은 점만 사람으로 인정
  (d) 머리 높이 평면 공식  머리 점 → 바닥 위치(m)
  (e) 칸에 넣기            바닥 위치가 어느 칸에 드는지 세기
        │
        ▼ 5장 평균
  칸별 사람 수 ÷ 걸을 수 있는 넓이 = density (명/㎡)
  모든 칸 사람 수 합 = count (구역 인원)
```

**(a) 왜 영상을 줄이나**: P2PNet은 머리가 깨알만 한 군중 사진으로 학습했다. 가까이서 찍은 CCTV의 큰 머리는 오히려 잘 못 알아보고, 빈 도로에서 105명을 찾아내기도 했다. 영상을 줄이면 머리 크기가 학습 사진과 비슷해져 잘 센다. 알맞은 배율은 영상마다 다르다. 카메라가 가까운 `E04_039`는 0.25배, 높이 9m에서 멀리 보는 `E05_035`는 0.7배였다.

**(c) 판정 기준**: 기준을 낮추면 놓치는 사람(미탐)이 줄지만 엉뚱한 것(오탐)이 늘어난다. 이것도 E2로 고른다.

**5장 평균**: 사람이 움직이면 장마다 가려지는 사람이 달라서 한 장만 세면 숫자가 들쭉날쭉하다. 앞뒤 0.4초 안의 5장을 평균하니 E2 오차가 27.5%에서 17.7%로 줄었다.

**개인정보**: 머리 점 좌표는 계산할 때 메모리에서만 쓰고 버린다. 파일에는 칸별 숫자만 남는다.

**결과물**: `data/processed/timeline/E04_039.json`. 이 단계에서는 `density`, `count`만 채우고 나머지 칸은 `null`(아직 없음)로 비워 둔다.

### ⑤ 흐름·불안정 (조영준, `src/flow/`)

사람들이 **어느 쪽으로, 얼마나 빨리, 얼마나 제각각** 움직이는지 잰다.

```
  t초 프레임 + 바로 다음 프레임 (1/30초 뒤)
        │
        ▼
  (a) 광학 흐름 (Farneback)   두 장을 비교해 화면 각 부분이 몇 픽셀, 어느 방향으로 움직였는지
        │                      (AI가 아닌 고전 계산법. DIS, RAFT도 비교 후보)
        ▼
  (b) 머리 주변만 보기          ④에서 찾은 머리 점 주변 픽셀의 움직임만 뽑는다
        │                      (머리 점은 파일이 아니라 메모리로 바로 넘겨받는다)
        ▼
  (c) 바닥 속도로 바꾸기        머리 높이 평면 공식으로 머리 이동 → 바닥 위 이동(m) ÷ 시간 = m/s
        ▼
  (d) 칸 평균                  칸 안 머리들의 속도를 평균 → vx, vy (칸의 대표 속도)
        │                      대다수와 반대로 움직이는 비율 → counterflow
        ▼
  (e) 흔들림 (speed_var)        최근 30초 동안 칸 대표 속도가 평균에서 얼마나 벗어났나
        │                      (사람이 없어도 생기는 화면 잡음만큼은 뺀다)
        ▼
  (f) 군중 압력 (pressure)      density × speed_var  ← "빽빽한데 마구 흔들린다"
        ▼
  (g) 유입 비율 (inflow_ratio)  화면 가장자리 칸에서 움직이는 픽셀 중
                                구역 안쪽을 향하는 비율 (사람이 있는 칸만)
```

- **군중 압력**은 2007년 메카 압사 사고 연구(Helbing)에서 나온 지표다. 0.02/s²를 넘고 약 10분 뒤 사고가 났다. 우리는 이 값을 처음 기준으로 쓰되 (가정), 실험(E5)으로 조정한다.
- **딥러닝 대신 공식을 쓰는 이유**: 진짜 압사 직전 영상이라는 학습 데이터가 거의 없고, 알림이 왜 울렸는지 설명할 수 있어야 하기 때문이다.
- **왜 머리 주변만 보나**: 몸 전체 픽셀에 바닥 공식을 쓰면 속도가 부풀려진다(`E04_039`에서 약 1.7배). 머리 점과 머리 높이 평면 공식을 쓰면 ④의 인원 세기와 같은 기준으로 맞춰진다.
- **현재 상태**: 11-11 결정에 따라 머리 높이 평면과 구역 설정 파일을 쓰도록 바뀌었다(#36). 흐름 계산은 ④의 머리 점을 메모리로 넘겨받아야 하므로, 영상을 넣고 한 번에 돌리는 실행은 통합 스크립트에서 한다. `counterflow`는 칸 단위로 계산하지만 아직 `timeline.json`에 쓰지는 않는다.

### ⑥ 60초 예측 (나예린, `src/predict/`)

1초마다 **그 시각까지의 최근 30초 밀도만** 보고 60초 뒤 밀도를 칸별로 예측한다. 미래 값을 몰래 쓰면 예측 시험(E6)이 무효가 된다.

| 예측 방법 | 쉬운 설명 | 성격 |
|---|---|---|
| 현재값 유지 (persistence) | "1분 뒤에도 지금과 같다" | 가장 단순한 기준선 |
| 직선 추세 (linear) | "최근 30초 동안 오른 속도로 계속 오른다" | 기준선 |
| 흐름 이동 (flow) | 칸마다 사람 수를 ⑤의 속도 방향으로 옮겨 본다. 물감이 물에 실려 흘러가는 계산(이류)과 같다 | 우리 방법 |

- 셋을 같은 영상에서 비교해 결과를 그대로 공개한다(E6). 합격 기준은 두지 않았다. 사전 측정에서 직선 추세가 현재값 유지보다 나쁜 경우가 있었기 때문이다.
- 설정은 `src/predict/config.yaml`에 있다 (예측 방법, 입력 30초, 예측 60초).
- 실행: `python -m src.predict.run --input …json --output …pred.json`
- 처음 29초는 입력이 30초가 안 돼서 예측값이 `null`이다.

### 📄 timeline.json: 세 사람이 함께 채우는 기록표

```json
{
  "schema_version": "0.2",
  "meta": {                                  ← 파일당 한 번: 영상·구역 정보, 칸 목록
    "zone_id": "zone-e04-039", "video_id": "E04_039", "duration_s": 180,
    "cells": [ { "cell_id": "c-0412", "walkable_area_m2": 3.2, "image_polygon": [...] } ]
  },
  "frames": [                                ← 1초에 한 줄
    { "t": 120, "count": 13.8, "inflow_ratio": 0.42,
      "cells": [ { "cell_id": "c-0412",
                   "density": 4.3,           ← ④ 이유노
                   "vx": 0.21, "vy": -0.05, "speed_var": 0.006,
                   "pressure": 0.0258, "counterflow": 0.12,   ← ⑤ 조영준
                   "density_pred_60s": 4.6 } ] }               ← ⑥ 나예린
  ]
}
```

- 파일에 **넣지 않는 것**: 위험 등급과 알림(서버가 판정), 머리 좌표·영상(개인정보).
- 등급을 파일에 넣지 않는 이유: 기준값(3명/㎡ 등)을 바꿀 때마다 분석을 다시 돌리지 않으려고, 판정은 서버 설정으로 뺐다.
- 아직 만들지 않은 값은 지우지 않고 `null`로 둔다. 그래서 서버와 화면은 처음부터 `null`을 처리하도록 만든다.
- 전체 규칙은 [timeline-spec.md](timeline-spec.md)에 있다.

## 2부. 시연

### ⑦ 서버: 재생과 판정 (조영준, Spring Boot, `server/`)

```
 timeline.json ──▶ 1초마다 한 줄 꺼냄 ──▶ 등급 판정 ──▶ 알림 결정 ──▶ WebSocket으로 화면에 전송
```

| 판정 | 규칙 (모두 (가정), 실험으로 조정) |
|---|---|
| 칸 등급 | 밀도 3명 이상 주의, 4명 이상 경계, 5명 이상 심각 |
| 구역 등급 | 걸을 수 있는 넓이 2㎡ 이상 칸의 등급 중 가장 높은 것 (작은 칸은 오탐 1명에도 튐) |
| 등급 올리기·내리기 | 2초 연속이면 올리고, 10초 연속 낮으면 한 단계 내림 (깜빡임 방지) |
| 불안정 | 군중 압력이 0.02를 3초 연속 넘으면 심각 조건 |
| 유입 경보 | 유입 비율 최근 5초 평균이 0.6을 넘으면 켬. 구역 인원(`count`)이 3명 미만이면 켜지 않음 |

- 서버 → 화면 메시지는 세 종류다: `hello`(연결 직후 구역 정보), `zone_state`(1초마다 상태), `alert`(알림). 자세한 규칙은 [api-spec.md](api-spec.md).
- **현재 상태**: 메시지 규격(api-spec)은 정했고 서버 코드는 아직 시작 전이다. G2(11-18)의 "알림 5초 이내"가 서버에 달려 있어 11-12부터 최우선으로 한다.

### ⑧ 화면: 상황실 대시보드 (나예린, React, `web/`)

- 영상 위에 칸별 밀도를 색으로 칠한 **히트맵**을 겹치고, 인원·밀도 **추세 그래프**, **알림 목록**, 등급 표시, 밀집 칸 목록을 한 화면에 보여준다.
- 지금은 `timeline.json` 파일을 직접 읽어 보여줄 수 있고, 가짜 WebSocket 서버(`web/scripts/mock-ws-server.mjs`)로 실시간 수신도 연습한다. 진짜 서버가 생기면 연결만 바꾼다.
- 영상과 기록표의 시각이 1초 넘게 어긋나면 화면이 영상 위치를 `t`에 맞춘다.

## 6. 알려진 한계

- **축척 가정**: 바닥 공식의 축척이 5% 틀리면 넓이는 약 10% 틀리고 밀도도 그만큼 틀린다. 영상마다 근거와 검증값을 구역 설정 파일에 남긴다.
- **렌즈 왜곡 무시**: 화면 가장자리가 휘어 보이는 효과는 계산에 넣지 않았다.
- **고밀도 정답 영상 부족**: 실제 압사 직전 같은 영상이 없어, 불안정 지표는 "감지 성능"이 아니라 "변화를 보여주는 지표"로 제시한다.
- **실시간 아님**: CPU로는 실시간보다 느리다. 처리 시간은 기록해 공개하고(E8), 실시간 입력은 여유가 있을 때 GPU로 시도한다.
- **영상별 설정**: 머리 찾기 설정값(축소 배율 등)은 영상마다 정답을 만들어 다시 골라야 한다.
